# 管线：十步，顺序不能换

交付不是一堆文件，是一条**确定性链**：数据层是唯一真源，图纸、方案书、PDF、交付包、验收门
全部从它派生。任何一段手抄了上一段的数字，抄的那一份就会在第三轮改动后变成假数字。

```
① 数据层  prepare_site      底图 DXF → 红线、地形、建筑、道路、现状符号 → site.json
② 设计    design_plant      在 site.json 上算出种植布点、分区、林缘线 → design.json
③ 派生量  stats             面积、株数、配比、工程量、覆盖率 → stats.json（唯一数字出口）
④ 图纸    make_sheets       stats.json + design.json → N 张 DXF（+ 每张 PNG 预览）
⑤ 合订    to_pdf            N 张 DXF → 图集 PDF（页数＝图纸张数，这是硬证据）
⑥ 文档    build_doc         stats.json + 图纸 PNG + 案例原图 → 方案书 .docx
⑦ 排版验  layout_check      把 docx 渲成 PDF 逐页看：图有没有被裁一半、字有没有压图
⑧ 打包    package           装配唯一交付目录（图纸/预览/方案书/案例原图/判读证据/读我）
⑨ 验收    xcheck            三端点名 + 手册图目 + 案例 + 落点 + 时效 + 引用断链，红字必须 0
⑩ 自测    xcheck --selftest 每条判据故意破坏一遍，门不响就是瞎门
```

（①② 可以合成一个 `prepare.py`，但**派生量必须单独落一份 JSON**——那是所有文案的数字出口。）

## 三条硬规矩

**1. 改过上游脚本，必须重跑它下游那一段。** 这是最容易骗自己的一件事：改了 `make_sheets.py`
里的图名，没重跑 `build_doc`，方案书里就还是旧图名，肉眼对着屏幕看不出来（你记得自己改过）。
所以把「谁生成谁」写成一张表交给 `gates_scaffold.py --fresh 产物表.csv` 去比 mtime：

```csv
产物,生成脚本
图集/PL-01_总平面.dxf,make_sheets.py
图集合订.pdf,make_sheets.py
方案书.docx,build_doc.py
最终交付_XX/方案书.docx,package.py
```

**2. 每段都要确定性。** 同一份输入跑两遍，产物字节级一致（或差异只在时间戳）。做法：随机种子
写死；遍历一律 `sorted()`；浮点打印统一小数位；不要 `dict` 迭代顺序依赖（3.7+ 虽然稳定，但
你改代码插一个键就变了）。跑两遍比对是验收的一部分，本项目就这么抓到过一次图例顺序抖动。

**3. 数字只有一个出口。** 方案书里出现「159 株」这种句子，必须由 `build_doc.py` 从
`stats.json` 现算填进去（`"...%d株..." % S["n_tree"]`），不能手打。手打的数字是第二个真源，
而第二个真源一定会走样。同理，**别在正文里做补数**（写 `100-x`）——现算可以，让正文自己减
就成了不可溯源的数。

## 卡点在哪（会卡住新手的三处）

- **图纸版面塞不下**：注记、图例、统计表挤在右栏，超出图框。做法是给右栏写一个自适应列数的
  装箱函数（先按 `w/215mm` 估列数，放不下就一列一列加，最后 assert 剩余高度 ≥0），别手写坐标。
  `dxf_sheet_scaffold.py` 的 `table()`/`check()` 是最小可用版本。
- **docx 插图被裁**：Word 的固定行距会把超高的图切掉。唯一可靠的查法是把 docx 转 PDF 逐页渲图
  （`pypdfium2`），看边缘。这就是第 ⑦ 段存在的理由。
- **改一处要动 19 张图**：图名、张数、比例这类全局量必须放注册表（一个 `SHEETS` 列表），
  所有脚本从它派生，并 assert「绘图脚本自报图名 == 注册表图名」。本项目真在加第 18 张图时
  被这条 assert 救过一次。
